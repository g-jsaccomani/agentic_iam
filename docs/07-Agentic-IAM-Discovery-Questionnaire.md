# Agentic IAM Discovery Questionnaire
**Google Cloud Consulting (PSO) — 7-Domain Sector-Calibrated IAM & Cloud Identity Posture Verification & Discovery Guide**

> **Repository Deliverable:** [docs/07-Agentic-IAM-Discovery-Questionnaire.md](07-Agentic-IAM-Discovery-Questionnaire.md)

> **Executive Summary:** This deep technical discovery and readiness questionnaire is the foundational stakeholder assessment instrument for Google Cloud Consulting (PSO) **IAM & Cloud Identity Posture Assessment, Modernization & Least-Privilege Acceleration** engagements. While the **Agentic IAM Accelerator** automatically inventories Google Cloud control-plane IAM bindings, Service Account keys, Workload Identity Pools, Organization Policies, IAM Recommender insights, and NetworkX escalation paths **100% read-only**, this calibrated 7-domain instrument captures off-cloud Workforce IdP/HR Joiner-Mover-Leaver (JML) processes, PAM approval governance, emergency break-glass procedures, CI/CD pipeline dependencies, third-party contractor lifecycles, and optional breach-impact parameters used to tailor the customer's 3-Wave Modernization Roadmap.

---

## 1. Questionnaire Overview, Consultative Rigor & Architectural Integration

An automated cloud control-plane scan reveals **what** permissions exist today (e.g., standing `roles/owner` grants, `>90d` static Service Account keys, unconditioned WIF providers, and multi-hop `TokenCreator` chains), but cannot by itself know whether a departed contractor is still active in an upstream HR system, which security committee should approve a 1-hour Privileged Access Manager (PAM) elevation, or whether an annual financial close batch job relies on a specific storage role. This 35-question instrument bridges automated telemetry and human organizational readiness.

### 1.1 Consultative Readiness Assessment vs. Statutory Certification Boundary

**Important Engagement Framing:** Under the Google Cloud Shared Responsibility Model, Google Cloud Consulting (PSO) conducts a **Consultative IAM Posture Assessment, Attack-Path Review, and Least-Privilege Modernization Advisory** — never a formal statutory, regulatory, QSA, or compliance certification audit. Every domain below is structured with verification-grade rigor, concrete evidence artifacts, and direct control traceability aligned with NIST SP 800-207 (Zero Trust), NIST SP 800-53 Rev. 5 (`AC-2`, `AC-5`, `AC-6`), CIS Google Cloud Foundation Benchmark, ISO/IEC 27001:2022 (`A.5.15–A.5.18`, `A.8.2`), PCI-DSS v4.0.1 (Req 7 & 8), EU DORA (Art. 9), and BACEN BCB 85/4893.

### 1.2 How This Questionnaire Connects to the Technical & Executive Suite

1. **Shapes Target PAM JIT & Group RBAC Architecture (`Agentic IAM Technical Architecture and Consultant Guide`):** Answers from Domains 1–3 define the customer's Cloud Identity Security Group taxonomy, PAM approver groups, maximum JIT grant durations (`1800s`–`14400s`), and break-glass alerting rules authored in `iam.tf` and `pam_entitlements.tf`.
2. **Validates Workload & CI/CD Cutover Sequencing (`Agentic IAM Security Recommendations Book`):** Answers from Domains 4–5 identify legacy batch jobs, external CI/CD runners (GitHub Actions, GitLab, Jenkins, Azure DevOps), and appliance constraints before enforcing `constraints/iam.disableServiceAccountKeyCreation` in `org_policies.tf`.
3. **Calibrates Crown-Jewel Prioritization & Optional Business Impact:** Answers from Domain 6 identify Tier-0 regulated datasets (PII/PHI/PCI/financial ledgers) and optional customer-supplied breach-cost ranges so NetworkX attack paths reaching Tier-0 crown jewels are prioritized into **Wave 1 (Days 0–30)**.

### 3.1 Domain 1 — Workforce Identity Federation (IdP/SSO), MFA/2SV & Joiner-Mover-Leaver Lifecycle (Weight: 15%)

1. **Q1.1 — Authoritative Workforce Identity Provider (IdP) & SSO Architecture:** Which Identity Provider serves as the single authoritative source of truth for human workforce identities accessing Google Cloud (e.g., Google Cloud Identity / Workspace native, Microsoft Entra ID, Okta, Ping Identity), and is SAML 2.0 / OIDC federation enforced for 100% of non-break-glass users? `[Evidence: Cloud Identity SSO Profile]`
2. **Q1.2 — Automated SCIM Provisioning & Leaver Deprovisioning SLA:** When an employee or contractor terminates or transfers departments in your HR system (Workday, SAP SuccessFactors, BambooHR), is Cloud Identity / Workspace account suspension automated via SCIM/GCDS, and what is the measured SLA from HR termination to active Google Cloud token revocation? `[Calibrates: JML Revocation SLA]`
3. **Q1.3 — Phishing-Resistant Multi-Factor Authentication (2SV / FIDO2 / Passkeys):** Is 2-Step Verification (2SV) mandatorily enforced (`isEnforcedIn2Sv = true`) across 100% of users, and are Organization/Security Administrators required to authenticate with phishing-resistant FIDO2 hardware security keys (Titan/YubiKey) or Passkeys rather than SMS/TOTP? `[Evidence: Directory 2SV Policy]`
4. **Q1.4 — Context-Aware Access (BeyondCorp Enterprise / Access Context Manager):** Are Google Cloud Console and `gcloud` API administrative sessions gated by Access Context Manager policies requiring corporate-managed endpoint posture (Endpoint Verification / CrowdStrike / Intune) and approved IP/geo boundaries? `[Evidence: Access Level YAML]`
5. **Q1.5 — Dormant & Orphaned Human Account Hygiene:** Does your IAM governance process automatically audit and remove IAM bindings belonging to suspended Cloud Identity accounts, unaccepted external invitations, or human principals with `0` Cloud Audit Log events over 90 days? `[Evidence: Quarterly Access Review Logs]`

### 3.2 Domain 2 — Cloud Identity Security Groups & Role-Based Access Control (RBAC) Taxonomy (Weight: 15%)

1. **Q2.1 — Direct `user:` IAM Assignment Prohibition:** Does organizational policy prohibit binding roles directly to individual `user:<email>` principals at the Organization, Folder, and Project levels in favor of `100%` group-based RBAC (`group:<role-persona>@<domain>`)? `[Evidence: CAI Group RBAC Adoption %]`
2. **Q2.2 — Locked Security Groups (`groups.security`) vs. Collaborative Discussion Groups:** Are all Cloud Identity groups referenced in GCP IAM policies created with the immutable `cloudidentity.googleapis.com/groups.security` label and `WHO_CAN_JOIN = INVITED_CAN_JOIN`, preventing employees from self-joining open discussion forums that carry cloud permissions? `[Evidence: Cloud Identity Group Labels]`
3. **Q2.3 — Group Ownership Accountability & Dual-Custody Governance:** Does every IAM-bound Cloud Identity group have at least two active `OWNER` or `MANAGER` custodians (preventing "ownerless orphaned groups"), and are membership additions gated by ticketing/IGA approval (e.g., Saviynt, SailPoint, Jira, or Google Groups expiration)? `[Evidence: Group Membership Audit]`
4. **Q2.4 — Transitive Group Nesting Depth Ceiling:** Does your group architecture enforce a flat or bounded nesting hierarchy (`<= 2` levels), avoiding deep multi-layer group nesting (`Vendor Group -> Dev Group -> Platform Group -> Folder Admin`) that masks effective blast radius? `[Calibrates: Max Group Nesting Depth]`
5. **Q2.5 — Persona-Aligned RBAC Naming & Scope Taxonomy:** Do you maintain a standardized group naming convention mapping job personas cleanly to hierarchy scopes (for example, `gcp-<bu>-<env>-<persona>@<domain>`) separating Platform Admins, Network Admins, Data Readers, App Deployers, and Security Auditors? `[Evidence: RBAC Design Doc]`

### 3.3 Domain 3 — Privileged Access Management (PAM Just-In-Time), Standing Primitives & Break-Glass (Weight: 20%)

1. **Q3.1 — Elimination of Standing Primitive Roles (`roles/owner` & `roles/editor`):** How many human users currently hold 24/7 standing `roles/owner`, `roles/editor`, `roles/resourcemanager.organizationAdmin`, or `roles/iam.securityAdmin` permissions, and what operational tasks currently require those standing grants? `[Evidence: CAI Primitive Bindings List]`
2. **Q3.2 — Google Cloud Privileged Access Manager (PAM) JIT Readiness & Approval Matrix:** Which security or platform teams (`<PAM-APPROVER-GROUP>`) should serve as mandatory approvers for 1-hour Just-In-Time **Privileged Access Manager (PAM)** elevations in production, and what maximum grant duration (`1800s`, `3600s`, `7200s`) aligns with your on-call incident response SLAs? `[Calibrates: pam_entitlements.tf Parameters]`
3. **Q3.3 — Emergency Break-Glass Account Architecture & Out-of-Band IdP Resilience:** How many super-admin break-glass accounts exist (`recommended: 2`), are they native Cloud Identity accounts excluded from external third-party IdP SAML outages, and where are their hardware FIDO2 backup keys physically vaulted? `[Evidence: Break-Glass SOP]`
4. **Q3.4 — Real-Time Break-Glass & PAM Elevation Monitoring:** Does any authentication or IAM mutation by a break-glass account (or unapproved privilege escalation) trigger an immediate P1 alert in Google Security Operations (Chronicle SIEM), SCC, or PagerDuty/Slack within `< 5` minutes? `[Evidence: Cloud Monitoring / SIEM Log Alert]`
5. **Q3.5 — Time-Bound IAM Conditions (`request.time`) for Temporary Access:** For temporary project troubleshooting, auditor reviews, or migration windows where PAM is not yet deployed, do engineers attach CEL expiry conditions (`request.time < timestamp("YYYY-MM-DDT00:00:00Z")`) so temporary access auto-expires without manual cleanup? `[Evidence: Conditional IAM Bindings]`

### 3.4 Domain 4 — Workload Identity Federation (WIF), Service Account Sprawl & Static Key Elimination (Weight: 20%)

1. **Q4.1 — User-Managed Static Service Account JSON Key Footprint (`>90d`):** Across CI/CD pipelines, developer laptops, on-premises servers, and multi-cloud scripts, which workloads still authenticate using downloaded `.json` Service Account private keys, and how many keys exceed 90 days without rotation? `[Evidence: collect_cai_service_account_inventory]`
2. **Q4.2 — External CI/CD & Multi-Cloud Workload Identity Federation (WIF) Adoption:** Which CI/CD and cloud platforms (GitHub Actions, GitLab CI, Bitbucket, Jenkins, Azure DevOps, AWS IAM, AKS/EKS) deploy to Google Cloud today, and are they ready to exchange OIDC/AWS tokens via **Workload Identity Federation** instead of storing static secrets? `[Calibrates: iam.tf WIF Pool Specs]`
3. **Q4.3 — WIF OIDC `attributeCondition` Hardening (Preventing Repo-Jacking):** On existing `WorkloadIdentityPoolProvider` resources (such as `https://token.actions.githubusercontent.com`), do you enforce strict CEL `attributeCondition` expressions pinning `assertion.repository_owner_id` (numeric immutable ID) and branch/environment claims so external public repos cannot impersonate internal Service Accounts? `[Evidence: WIF Provider Configs]`
4. **Q4.4 — Retirement of Default Compute Engine & App Engine Service Accounts:** How many GCE VMs, Cloud Run services, Cloud Functions, Dataflow jobs, or Vertex AI notebooks still execute under `<project-number>-compute@developer.gserviceaccount.com` or `@appspot.gserviceaccount.com` with inherited `roles/editor`, rather than 1 dedicated least-privilege Service Account per microservice? `[Evidence: Default SA Workload Map]`
5. **Q4.5 — Legacy Appliance Exceptions for `iam.disableServiceAccountKeyCreation`:** Are there any third-party COTS appliances, mainframes, or OT edge devices incapable of OIDC or X.509 certificate-based Workload Identity Federation that require a documented resource-tag exception before enforcing `constraints/iam.disableServiceAccountKeyCreation` Organization-wide? `[Evidence: Key Exception Register]`

### 3.5 Domain 5 — Multi-Hop Impersonation Chains, Custom Roles & Separation of Duties (Weight: 10%)

1. **Q5.1 — Project-Wide vs. Resource-Scoped `TokenCreator` & `serviceAccountUser` Grants:** Are `roles/iam.serviceAccountTokenCreator` and `roles/iam.serviceAccountUser` bound strictly on the individual target Service Account resource, or are they granted at the Project or Folder root (allowing lateral impersonation of *every* Service Account in that scope)? `[Evidence: NetworkX Choke-Point Graph]`
2. **Q5.2 — Cross-Project Service Account Hop Chains (`Apps -> Data -> SecOps`):** Which shared CI/CD, Terraform, or data-orchestration Service Accounts intentionally impersonate downstream Service Accounts across project boundaries, and are those hops documented and restricted by IAM Conditions? `[Evidence: Cross-Project SA Matrix]`
3. **Q5.3 — Custom IAM Role Governance & Self-Escalation Permissions (`iam.roles.update`):** How many Organization-level and Project-level Custom Roles exist today, who reviews their `includedPermissions`, and do any operational custom roles dangerously combine `iam.roles.update`, `iam.serviceAccounts.getAccessToken`, or `resourcemanager.*.setIamPolicy`? `[Evidence: Custom Role Inventory]`
4. **Q5.4 — Cloud KMS Cryptographic Separation of Duties (SoD):** Is strict Separation of Duties enforced so that no single human administrator or Service Account simultaneously holds `roles/cloudkms.admin` (key lifecycle/policy management) AND `roles/cloudkms.cryptoKeyEncrypterDecrypter` (data decryption) on production CMEK keyrings? `[Evidence: KMS IAM Policy Review]`
5. **Q5.5 — Centralized Audit Log Integrity & Sink Tampering SoD:** Are Organization/Folder Cloud Audit Log sinks (`_Required`, `_Default`, and SIEM BigQuery/PubSub sinks) managed in a dedicated `sec-mgmt` project where application/project admins hold **zero** `roles/logging.configWriter` (`logging.exclusions.create` / `logging.sinks.delete`) permissions? `[Evidence: Logging Sink IAM Policy]`

### 3.6 Domain 6 — External/Partner Governance (DRS), Public Exposure Prevention & Data Perimeters (Weight: 10%)

1. **Q6.1 — Domain Restricted Sharing (`constraints/iam.allowedPolicyMemberDomains`):** Which external partner, subsidiary, or B2B vendor Cloud Identity `directoryCustomerId` values (`C0...`) have legitimate business approval to hold IAM bindings in your environment, and can `allowedPolicyMemberDomains` be enforced across all internal folders? `[Calibrates: org_policies.tf Allowed Customer IDs]`
2. **Q6.2 — Consumer Account (`@gmail.com`) & External Contractor Lifecycle:** Are external consultants and contractors provisioned corporate `@<customer-domain>` contractor identities (with automatic 90-day HR expiration), or have consumer `@gmail.com` / third-party vendor emails been granted direct IAM access? `[Evidence: External Principals Report]`
3. **Q6.3 — Public Exposure Prevention (`allUsers` / `allAuthenticatedUsers`):** Are `constraints/storage.publicAccessPrevention` and `constraints/run.allowedIngress` / Cloud Run IAM checks enforced Organization-wide, with explicit resource-tag exceptions only for intentionally public marketing CDNs or public APIs? `[Evidence: Public Principals Scan]`
4. **Q6.4 — Tier-0 Crown-Jewel Identification & VPC Service Controls (VPC-SC):** Which GCP projects, BigQuery datasets, Cloud Storage buckets, and Secret Manager vaults hold regulated Tier-0 data (PII, PHI, PCI cardholder data, financial ledgers, proprietary AI weights), and are they enclosed inside **VPC Service Controls** perimeters to block token-replay exfiltration from external networks? `[Calibrates: Tier-0 Crown-Jewel Scope]`
5. **Q6.5 — Optional Business-Impact & Breach-Cost Calibration Inputs:** If executive leadership requests quantitative risk-exposure ranges in the Week 4 readout, what are your organization's internally validated record volumes, Business Impact Analysis (BIA) outage/breach cost ranges, cyber-insurance deductibles, and applicable statutory fine frameworks (e.g., LGPD, GDPR, PCI-DSS, DORA)? *(Optional — Agentic IAM never invents financial figures.)* `[Evidence: Customer BIA / Risk Register]`

### 3.7 Domain 7 — IAM Infrastructure-as-Code (Terraform/OpenTofu), Policy Simulator CI/CD & Drift Guardrails (Weight: 10%)

1. **Q7.1 — Declarative IAM-as-Code Coverage vs. ClickOps Drift:** What percentage of Organization, Folder, and Project IAM policies, Custom Roles, and Organization Policies are managed declaratively in Git via Terraform/OpenTofu versus ad-hoc Google Cloud Console / `gcloud` changes? `[Calibrates: IaC Adoption %]`
2. **Q7.2 — Authoritative vs. Additive Terraform IAM Resource Strategy:** Do your Terraform modules use authoritative bindings (`google_project_iam_policy` / `google_project_iam_binding` — which automatically overwrite unauthorized console drift) or additive `google_project_iam_member` resources, and how is state partitioned across landing-zone vs. application repos? `[Evidence: Landing Zone IAM Module]`
3. **Q7.3 — Automated Pre-Merge Policy Simulator & IAM Recommender Cadence:** Does your CI/CD pull-request pipeline invoke **Google Cloud Policy Simulator** (`policysimulator.googleapis.com`) before applying IAM or Organization Policy changes, and is there a monthly SecOps workflow reviewing `google.iam.policy.Recommender` insights? `[Evidence: CI/CD IAM Pipeline YAML]`
4. **Q7.4 — IAM Deny Policies & Resource Tags for Hard Guardrails:** Has your architecture adopted **IAM Deny Policies** (v2) and immutable **Resource Manager Tags** (`tagValues/*`) to enforce non-bypassable guardrails that cannot be overridden even by Project `Owners`? `[Evidence: IAM Deny Policies]`
5. **Q7.5 — Continuous CIEM Drift Detection & Auto-Remediation:** Is Security Command Center (SCC) CIEM / Cloud Asset Inventory real-time Pub/Sub feed monitoring enabled to alert SecOps whenever a primitive `Owner` binding, static SA key, or Organization Policy override is created outside your CI/CD pipeline Service Account? `[Evidence: CAI Real-Time Feed / SCC Config]`
