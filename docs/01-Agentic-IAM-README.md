## 1. Agentic IAM Explained in 2 Minutes (For Non-Specialists)

If you are new to Cloud Identity and Access Management (IAM) posture modernization, here is the entire story in five simple points:

- **The Everyday Analogy (Hotel Master Keys vs. Timed Room Keycards):** Imagine a 50-floor hotel where contractors, developers, and automated robots were handed permanent "Master Keys" (`Owner` or `Editor` roles) that open every vault, server room, and executive suite 24/7 — even when they only needed to paint one hallway. Zero-Trust IAM replaces permanent master keys with **scoped keycards** (Least-Privilege Custom Roles) and **temporary 1-hour check-out passes** (Privileged Access Manager Just-In-Time access).
- **Why Is This Urgent Today? ("Attackers Don't Break In — They Log In"):** Across global cloud incident reports, compromised credentials, leaked Service Account JSON keys, and over-privileged CI/CD pipelines remain the #1 root cause of cloud breaches. Even when an attacker compromises a low-level test account, hidden **impersonation chains** (`Account A` can act as `Account B`, which can read `Production Database C`) let them escalate to full administrative control in seconds.
- **What Are PAM JIT & Workload Identity Federation (WIF)?** Instead of giving admins 24/7 standing `Owner` rights, **Privileged Access Manager (PAM)** grants temporary 1-hour elevation only after approval and logs every action. Instead of downloading static Service Account JSON keys that never expire, **Workload Identity Federation (WIF)** exchanges short-lived cryptographic tokens automatically — zero downloadable keys to leak!
- **Why Do Companies Struggle to Clean Up IAM?** A medium or large enterprise has tens of thousands of IAM bindings across hundreds of projects, nested Cloud Identity groups, and legacy Service Accounts. Tightening permissions manually with spreadsheets takes months — and teams are terrified that revoking an unused permission will accidentally break a production payment API at 2:00 AM.
- **What is Agentic IAM?** Agentic IAM is Google Cloud's intelligent posture assessment and least-privilege accelerator. Built as a hybrid of deterministic Python and five **Google ADK** agents running **Gemini (`gemini-3.1-pro-preview-customtools`)** on Vertex AI (`location=global`), our **100% read-only** deterministic collectors inspect Cloud Asset Inventory, Cloud Identity groups, IAM Recommender, bounded Cloud Audit Log samples, and Organization Policies in minutes. A dedicated **NetworkX Graph Engine** maps every hidden privilege-escalation path, while Gemini specialists correlate IAM Recommender insights and observed Cloud Audit Log samples into a typed remediation plan that deterministic code renders as **advisory (unvalidated) Terraform/OpenTofu modules, Custom Roles, and PAM JIT entitlements** — giving Google Cloud Consultants an evidence-backed 6-week modernization blueprint while leaving Policy Simulator validation and all production changes under the customer's own CI/CD governance.

## 7. How the AI Agent Works (Architecture in Brief)

- **Gemini does the synthesis and reasoning.** A root coordinator agent (`iam_coordinator`) built on **Google ADK (`Runner`)** and Vertex AI (`gemini-3.1-pro-preview-customtools`, `GOOGLE_CLOUD_LOCATION=global`) orchestrates four domain-specialized Gemini sub-agents: `triad_analyzer`, `attack_path_agent`, `recommender_agent`, and `iac_generator`.
- **Deterministic Python & NetworkX tools collect 100% live evidence.** Read-only collectors (`cai_collector.py`, `directory_collector.py`, `graph_engine.py`, `recommender_tool.py`) query live Cloud Asset Inventory, Resource Manager v1/v3, IAM v1, IAM Credentials, Cloud Identity, Policy Analyzer, Recommender, bounded Cloud Logging samples (reporting `is_sample`, `sample_size`, observed window, and project coverage), and existing Policy Simulator metadata (no replay executed) — building a real `nx.DiGraph` with `betweenness_centrality` and `degree_centrality` before any LLM reasoning occurs.
- **Hybrid 18-control security framework scoring (`posture_scoring_engine.py`).** Every percentage is anchored on **18 deterministic `numerator / denominator` controls** (`22% Internal + 18% External + 22% Workload + 20% Least-Privilege + 18% Graph Resilience`) mapped to **Google Cloud Security Blueprint**, **NIST SP 800-53 Rev. 5**, **NIST CSF 2.0**, **CIS Google Cloud Benchmark v3.0**, and **CISA Zero Trust Maturity v2.0**, refined by bounded `[-5.0%, +5.0%]` Google ADK contextual calibration and a NIST/CISA Critical Exposure Ceiling.
- **Zero synthetic data & zero silent fallbacks.** Every principal, project ID, role, resource URI, permission count, and key age cited in the UI or exported reports comes strictly from live Google Cloud APIs. If permissions or APIs are missing, the 6-point pre-flight check and API endpoints surface explicit HTTP errors (`401`, `403`, `412`) rather than fabricated demo numbers.
- **Full ADK execution transparency.** Every scan and chat turn records `AdkExecutionTelemetry` (`model_version`, `agents_invoked`, `llm_steps`, `input_tokens`, `output_tokens`, `thought_tokens`, and per-tool execution latency in milliseconds).
- **Deep Accounts, Keys, KMS & Secrets Vault visibility (`asset_key_secret_inventory.py`).** 100% metadata-only inspection across Human/Group/External Accounts, Service Accounts, `USER_MANAGED` & `SYSTEM_MANAGED` SA Keys, Secret Manager Secrets (replication, CMEK, rotation & IAM accessors — zero secret payload reads), Cloud KMS `KeyRing`/`CryptoKey` rotation & SoD conflicts, Google Cloud API Keys, Custom IAM Roles, Workload Identity Pools, and Organization Policies.
- **Complete 7-section executive deliverables out of the box.** Generates zero-truncation Word (`.docx`) and PDF (`.pdf`) books containing all 18 framework controls, all 8 credential/vault ledgers, high-DPI NetworkX Attack Graph & Choke-Point Centrality (`.png`), all 5 OpenTofu/Terraform HCL modules (`.zip`), 3-Wave Roadmap, ADK tool trace, and Inventory JSON (`.json`).

## 8. Portal Security, Clean-Slate Multi-User Isolation & Sign-In

Because IAM telemetry is among an enterprise's most sensitive metadata, `agentic_iam_accelerator` enforces a **Zero-Trust Clean-Slate Multi-User Architecture** across two strictly separated planes (`backend/identity_guard.py`, `backend/session_vault.py`, `backend/main.py`):

- **Cloud Run Native Identity-Aware Proxy (`--iap --no-allow-unauthenticated`) & Signed Session Binding.** Every edge request is authenticated by Google Cloud's native Cloud Run IAP (`X-Goog-IAP-JWT-Assertion`) or verified Google OAuth2/OIDC token validation and bound to an HMAC-SHA256 signed `HttpOnly`, `Secure`, `SameSite=Lax` ticket (`iam_consultant_ticket`) carrying a unique cryptographic `session_id` (`sid`).
- **Strict Separation of AI Compute Plane vs. Target Inspection Plane.** In the default and recommended mode, the Cloud Run runtime Service Account (`sa-agentic-iam-engine`) holds **no** permission on any customer resource (no customer Organization, Folder, Cloud Asset Inventory, or BigQuery dataset); on the host project it holds `roles/aiplatform.user` and `roles/logging.logWriter` to execute Vertex AI Gemini calls, plus access to the private workspace bucket and its master secret described below. **Optional persistent auto-renew (OFF by default):** only if the deployment sets `IAM_ENABLE_PERSISTENT_DELEGATION=true` **and** the consultant ticks the explicit option when generating the onboarding kit, the kit additionally grants `roles/iam.serviceAccountTokenCreator` on the customer's `sa-iam-assessor` to this runtime Service Account so sessions can be renewed without the consultant's token; the platform then holds standing read-only access to that Organization until the customer removes that binding, and revoking the consultant's own grant does not remove it (the offboarding snippet in the kit removes both bindings). `cai_collector.py` never falls back to `google.auth.default()` in web mode; unconfigured sessions return `HTTP 412 Precondition Failed` with a 100% blank console.
- **Keyless 1-Hour Service Account Impersonation & Encrypted Per-User Workspace.** Each authenticated user connects their own or their customer's GCP Organization via `POST /api/v1/session/connect`, minting a short-lived 1-hour token via `iamcredentials.googleapis.com/...:generateAccessToken` against `sa-iam-assessor@<CUSTOMER_SEED_PROJECT>.iam.gserviceaccount.com` (where, in the default mode, the customer granted `roles/iam.serviceAccountTokenCreator` only to the named consultant `user:<authenticated_user_email>`, and the token is minted with that consultant's own OAuth token). Per-session caches are `ContextVar`-propagated across worker threads via `run_pool_map_with_context`. Each signed-in consultant also has a private persistent workspace keyed to their Google identity, which stores the connection record, the latest posture book, inventory and scan history so work survives browser closes; users never see each other's data. It is stored in a private Cloud Storage bucket in the consultant's host project (uniform bucket-level access, public access prevention), and every stored document is encrypted by the application with AES-256-GCM using a per-user key derived from a master secret held in Secret Manager, in addition to Google's default encryption at rest. Retention is chosen by the consultant when connecting a customer: `0` days means nothing is persisted (session-only, in memory); otherwise 1 to 365 days (default 30). Expired data is deleted by the application and by a bucket lifecycle rule, and **Disconnect & Wipe** (`POST /api/v1/session/disconnect`) deletes the workspace data immediately. The browser session cookie lasts 8 hours, and the service runs as a single Cloud Run instance behind Identity-Aware Proxy.
